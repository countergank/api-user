# Commit — Priority P0

Read this file before writing any commit message in this repository; start from `assets/COMMIT_TEMPLATE.txt` for the ready-made skeleton.

## P0 — Open every commit with one of the eleven Conventional Commit types

Write every commit header as `type(scope): description` — the scope is optional — followed by an optional body and optional footers, each new section separated from the previous one by a blank line.

Pick exactly one of the eleven canonical types and match it to the change actually made, not to its perceived importance:

| Type | Description | SemVer impact |
|------|-------------|---------------|
| `feat` | New feature or user-visible capability | `MINOR` |
| `fix` | Bug fix that corrects broken behavior | `PATCH` |
| `docs` | Documentation-only changes (README, guides, comments) | None |
| `style` | Formatting, whitespace, semicolons — no logic change | None |
| `refactor` | Restructuring that neither fixes a bug nor adds a feature | None |
| `perf` | Change that improves runtime or memory performance | `PATCH` |
| `test` | Adding or correcting tests — no production code change | None |
| `build` | Build system or external dependency changes | None |
| `ci` | CI/CD configuration changes | None |
| `chore` | Maintenance, tooling, config — no user-facing change | None |
| `revert` | Reverting a previous commit (auto-generated by `git revert`) | Inverse of original |

Map team aliases to the canonical type before committing: `bug`/`bugfix`/`hotfix` → `fix`, `feature` → `feat`, `doc`/`documentation` → `docs`, `formatting`/`lint` → `style`, `cleanup`/`restructure` → `refactor`, `deps`/`dependency` → `build`, `maintenance`/`task` → `chore`.

The type drives the version bump: `feat` bumps the MINOR version (`1.2.0` → `1.3.0`), `fix` and `perf` bump the PATCH version (`1.2.0` → `1.2.1`), and `feat` combined with a `BREAKING CHANGE` footer bumps the MAJOR version (`1.2.0` → `2.0.0`). Every other type stays internal by default and triggers no version bump.

```text
// ✅ Canonical types matched to the change
feat(auth): add OAuth2 login with Google provider
fix(api): handle null user preferences
chore(deps): update eslint to v9.0.0
```

```text
// ❌ Invented or inappropriate types
update(auth): change login flow
wip: working on user profile
```

## P0 — Write the subject in the imperative, lowercase, in 50 characters

Keep the subject line at 50 characters or fewer (72 characters is the absolute maximum), start the description after `type(scope): ` in lowercase, use the imperative mood ("add", not "added" or "adds"), and never end the subject with a period — it is a title, not a sentence. Separate the subject from the body with one blank line so tools such as `git log --oneline` and the PR view treat the first line as the summary; the test is "If applied, this commit will \<subject\>".

A specific subject beats a broad one: `login` beats `auth` when the change is login-specific, and `auth` beats `backend`.

Name scopes in lowercase kebab-case, keep them to 1-3 words, and reuse the same scope names across commits that touch the same area. Pick the scope from the area the change touches — `auth`, `login`, `oauth` for authentication; `api`, `routes`, `controllers` for the API layer; `db`, `models`, `migrations` for the data layer; `ui`, `components`, `styles` for the frontend; `config`, `env` for configuration; `tests`, `e2e` for testing. Omit the scope when no single scope applies, as in `feat: add dark mode support`.

```text
// ✅ Imperative, lowercase, no period, 50 characters or fewer
feat(auth): add Google OAuth2 provider
fix(api): handle null user preferences
docs: update contribution guidelines
```

```text
// ❌ Past tense, capitalized, trailing period, or no type prefix
feat(auth): Added Google OAuth2 login.
fix: fix the thing that was broken
update the user model to support fields
```

## P1 — Explain why in the body and keep footers on their own lines

Use the body to explain what changed and why it was needed; the diff already shows how, so do not narrate line-by-line changes. Wrap each body line at 72 characters — terminal and diff viewers truncate longer lines — and separate paragraphs with a single blank line. Skip the body for trivial changes such as typo fixes.

Put structured metadata in footers, each on its own line after one blank line following the body: `BREAKING CHANGE: <impact>`, `Closes #123` / `Fixes #123` / `Resolves #123` to close an issue, `Refs #456` to reference without closing, and `Co-authored-by: Name <email>` to credit a collaborator. Use one footer per line, and use as many footers as the change needs.

```text
// ✅ Body explains motivation, footers on their own lines
refactor(auth): extract token validation logic

The validation logic was tightly coupled to the route handler,
making it hard to test and reuse. It now lives in a dedicated
service with clear input and output contracts.

Refs #78
```

```text
// ❌ Footer glued to body text and wrap limit ignored
refactor(auth): extract token validation logic
The validation logic was tightly coupled to the route handler, making it hard to test and reuse. Refs #78
```

## P1 — Mark a breaking change with ! and a BREAKING CHANGE footer

Signal a breaking change with the `!` suffix on the type (`feat!:` or `fix!:`) AND include a `BREAKING CHANGE` footer; use both together for maximum visibility. The `!` makes the break visible at a glance in `git log --oneline`, while the footer describes what changed, the impact on consumers, and the migration steps they must take. Prefer warning through a deprecation period before breaking in a later release.

Write the footer as `BREAKING CHANGE: <description of impact>` so reviewers and release tooling parse it consistently, wrapping its lines at 72 characters like the body.

```text
// ✅ ! in the header plus a footer with migration steps
feat(api)!: change users response to an object

BREAKING CHANGE: /api/users now returns { data: [...] }
instead of [...]. Unwrap the response from the data key.

Closes #91
```

```text
// ❌ Breaking change hidden in a regular commit
feat(api): change users response to an object
```

## P2 — Map commit types to CHANGELOG sections

Write the CHANGELOG from the commit types in the history, never by hand from memory, following the [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format. Map each commit type to its section:

| Commit type | CHANGELOG section | SemVer impact |
|-------------|-------------------|---------------|
| `feat` | **Added** | `MINOR` |
| `fix` | **Fixed** | `PATCH` |
| `perf` | **Changed** | `PATCH` |
| `refactor` | **Changed** | None |
| `revert` | **Removed** | Inverse of original |
| `BREAKING CHANGE` | **Breaking Changes** (top of release) | `MAJOR` |
| `docs`, `style`, `test`, `chore`, `build`, `ci` | Omit — internal | None |

Keep breaking changes at the top of each release so consumers see them first, and leave the internal types out of the published entries.

```text
// ✅ Sections derived from the commit types
### Added
- OAuth2 login with Google provider (#42)

### Fixed
- Return 404 for missing resources instead of 500 (#91)

### Breaking Changes
- `/api/users` returns an object instead of an array
```

```text
// ❌ Section invented from memory, fix entry lost
### Changes
- OAuth2 login with Google provider (#42)
```
